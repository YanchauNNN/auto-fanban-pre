# 计算书 AI 规范化与封面六格编码设计

## 目标

修复非标准配筋表的 AI 响应因无关附加字段导致整任务失败的问题，并为内部结构、核岛厂房两种计算书的封面六格编码增加 YAML 驱动的业务规则。

## 封面六格编码

六格依次为：项目代码第 1 位、项目代码第 2 位、固定字母 `X`、厂房代码第 1 位、厂房代码第 2 位、层位码。

- 项目代码来自 `documents/参数规范.yaml` 的项目枚举；已确认的出图业务映射为 `1418=HL`、`1818=PC`、`1907=SM`、`1915=HP`、`1916=FY`、`2016=JD`、`2026=XZ`。
- `2035` 暂无两位代码，但不阻断任务；前两格留空并生成任务提醒。
- 第三格固定值、组合格式、缺失项目代码策略均由 YAML 描述。
- 第四、五格取现有 `subproject_code`，必须为两个大写字母。
- 第六格新增 `level_code`，由 YAML 表单向前端暴露，必填、单个英文字母、统一转大写。
- 后端只实现通用配置读取、校验和六格上下文组装，不复制项目代码、固定字母或校验表达式等业务常量。

## AI 输出与后端读取

Skill 和系统提示明确要求只返回一个最小 JSON 对象，并给出 `review_sources` 的完整最小示例。

后端采用“宽容读取、严格业务校验”两层策略：

1. 从纯 JSON、Markdown JSON 代码块或带少量说明的回复中提取 JSON 对象。
2. 忽略协议对象中的未知无效附加字段，例如 `review_sources[].wall_id` 和 `source_cells`。
3. 必需字段、字段类型、schema version、来源行、duplicate 范围、issue patch 守恒以及全局源行数仍严格校验。
4. AI 返回的 `actual_area` 等后端计算字段永不进入计算书业务结果。
5. 若第一次结果仍无法通过协议校验，则向同一模型发送只包含安全错误类别和目标 schema 的纠正请求；纠正次数由 `documents/参数规范-3.yaml` 配置。达到上限仍不合格才明确失败。

## 数据流

前端加载 `/api/form-schema` → YAML 字段生成层位码输入 → 创建/预检提交 `level_code` → 后端 Pydantic 校验 → YAML 项目代码和固定段组装六格 → DocxTemplate 渲染两种模板。

非标准配筋表由 Worker 调用规范化 Skill → 提取候选 JSON → 宽容结构解析 → 严格业务校验 → 必要时纠正重试 → 生成 Word 或返回安全失败信息。

## 验证

- 后端单元测试覆盖带额外字段、代码块/说明文字、多个候选对象、缺必需字段、纠正成功及纠正耗尽。
- 表单/API/模型测试覆盖层位码必填、单字母和大写归一化。
- 前端测试覆盖 YAML 字段渲染、必填与格式提示、预设保存恢复。
- 模板测试及 Word 渲染确认 `2016 + NH + R` 输出为 `JDXNHR`，2035 前两格留空但任务继续。
- 使用真实 RAR 和开发 MiniMax 做正式任务烟测。
