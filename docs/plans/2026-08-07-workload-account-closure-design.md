# 工作量闭环与账号管理界面重构设计

## 背景与目标

当前系统已经具备账号、任务包、审批、归档和工作量的后端基础能力，也已有工作量与账号页面，但仍有四个影响实机使用的断点：任务包详情页没有正式提交入口；管理动作写入 `group.json` 后未统一刷新生产模式使用的 SQLite 摘要索引；归档重试成功后没有复用首次归档成功的结算逻辑；工作量与账号页面的信息密度和操作层级不够稳定。

本轮目标是把“任务生成完成 -> 创建人提交 -> 一审/二审/三审 -> 自动归档 -> 工作量结算 -> 页面查询”闭合，并在不改变部署连接方式、不新增顶级模块入口的前提下，重构工作量和账号管理页面。

## 方案比较

### 方案 A：在现有任务包详情中补流程区，并抽取统一完成协调器（采用）

- 任务包详情继续复用现有作业详情和产物下载，只增加任务包管理查询及提交/冲突处理区。
- 后端以一个幂等的“归档成功后处理”服务统一完成结算、任务包成功状态和摘要刷新，首次归档与重试归档共用。
- 工作量和账号仍使用现有模块标签，在模块内部重排信息层级。

优点是边界清楚、改动集中、部署风险最低，也不会产生第二套任务详情或管理入口。

### 方案 B：只在工作量页面增加提交按钮

实现较快，但提交动作与任务产物、生成状态和冲突原因分离，创建人必须先理解工作量监控才能提交，不符合任务详情承接任务操作的心智模型。

### 方案 C：新增统一管理中心

可以把账号、审批、归档和工作量放进一个新页面，但会重复现有模块标签和平台导航，扩大路由、权限和部署回归面。本轮不采用。

## 后端设计

### 提交就绪校验

`TaskGroupService.submit` 在归档身份和重复任务冲突检查前，先验证：

1. 任务包本身已经完成生成；
2. 至少存在一个子任务；
3. 所有子任务均已成功；
4. 子任务声明的必要产物真实存在；
5. 当前用户是任务创建人，且流程仍处于可提交草稿状态。

校验失败返回稳定的业务错误码，前端展示明确原因，不进入审批流。序列化的 `can_submit` 必须复用同一套只读就绪判定，避免按钮可点但后端拒绝。

### 统一持久化与摘要发布

任务包管理服务接收一个可选的 `group_updated` 回调。所有会改变任务包摘要的管理动作在 `GroupManager.update_group` 后调用该回调；生产装配时绑定 `runtime.refresh_summary_index("group", group_id)`。这样 API 与独立 worker 模式仍以 SQLite 摘要为列表真源，但提交、审批、节点修复、账号引用重绑和归档结果会及时反映到任务列表。

### 归档成功后处理

新增小型、幂等的任务包完成协调器，职责仅包括：

- 按 YAML 的 `settlement_trigger` 执行工作量结算；
- 将任务包标记为成功；
- 持久化并发布最新摘要。

`TaskGroupService.approve` 和 `ArchiveRetryWorker` 都调用同一协调器。归档失败仍记录失败状态；重试成功不能只复制文件，必须完成结算与状态发布。重复调用不得产生重复贡献人记录或重复累计。

### YAML 一致性

业务规范中需要保留的人员字段统一使用代码当前读取的 `workflow.preserve_fields`，其中包含 `ied_discipline_leader`。本轮不把计算书/AI任务纳入工作量，因为其工作量口径尚未定义。

## 前端设计

### 视觉命题

采用“核电工程调度台”风格：低饱和蓝灰底、深蓝文字、单一蓝色主操作、绿色只表示可执行/已完成，红色只表示异常。去除重复大图和卡片拼贴，用分栏、细分隔线、紧凑状态条建立层级。

### 内容布局

任务包详情：

- 顶部保留返回、任务名称、生成状态和产物操作；
- 在产物概览之前增加一条紧凑流程带，显示草稿、各 YAML 审批节点、归档；
- 创建人在任务生成完成后看到“提交审批”；审批人看到当前节点和工作量系数入口；
- 冲突继续使用现有确认对话框，确认后带覆盖/取消旧流程参数重提。

工作量模块：

- 首屏顶部只保留模块标题、四个关键数字：待我审批、流程中、归档异常、当前范围累计 A1；
- 主区采用左侧“待办与流程”、右侧“统计与记录”的双栏结构；
- 流程卡突出唯一下一动作，元数据和节点轨道保持一行可扫读；
- 统计范围、日期、状态和有效记录筛选合并为一条工具栏；列表在模块内部滚动，避免整页频繁滚动。

账号模块：

- 个人页使用“身份摘要 + 安全操作 + 最近结算”三段式横向工作台；修改密码是明确但次级操作；
- 管理员页使用“账号目录/异常行”左栏与“创建或编辑表单”右栏；归档根目录放在顶部设置条，不和账号录入混排；
- 账号目录提供本地搜索，异常行数量始终可见。

### 交互命题

1. 页面切换和内容刷新只使用轻量透明度/位移动画，不引入新动画依赖；尊重 `prefers-reduced-motion`。
2. 可审批、可提交、归档失败三种状态通过颜色、文字和按钮同时表达，不仅依赖颜色。
3. 1600×900 尽量完整显示工具栏和主操作；1366×768 保持标题、关键数字和主要动作可见，其余长列表在面板内部滚动。

## 连接与部署保护

不修改 `resolveApiBaseUrl`、`useApiAdapter`、`viteProxy` 或生产 IIS/ARR 连接约定。前端默认继续发送同源 `/api` 请求；开发与预览继续由 `VITE_API_PROXY_TARGET` 转发，默认 `http://127.0.0.1:8010`。现有连接单测和构建必须继续通过。

## 错误处理

- 后端业务错误使用稳定错误码；前端转换为中文可执行提示。
- 任务包详情同时加载作业详情与管理详情，二者独立展示加载/失败状态；产物下载不因管理详情暂时失败而消失。
- 提交成功后刷新任务包详情、作业详情、任务列表、流程监控和当前账号待办数。
- 重试归档成功后由后端主动刷新摘要，不依赖浏览器偶然轮询修正。

## 验收标准

- 未完成或存在失败子任务的任务包不能提交，且 `can_submit` 为假。
- 可提交任务包能在详情页完成提交；两类冲突均能人工确认后重提。
- API 与 worker 分离时，提交、审批、归档重试后的 `/api/jobs` 状态及时一致。
- 归档重试成功后任务包成功、工作量已结算且贡献人不重复。
- 工作量、个人账号、账号管理页面在 1600×900 和 1366×768 下主操作无需整页滚动即可到达。
- 账号和工作量仍复用现有模块标签，平台标题仍位于模块标签上方。
- 前端目标测试、完整 `npm test`、`npm run build`，后端目标测试及新增生产模式集成测试全部通过。
