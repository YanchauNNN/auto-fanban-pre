## 1. 文档目的

本文档面向前端工程师，目标是把以下 3 条业务线拆成可直接执行的前端实施计划：

- 登录、账号管理、权限驱动展示
- 最近任务与提交流程入口
- 工作量流程监视、审批交互与统计页面

本计划默认基于现有前端技术栈：

- React 18
- TypeScript
- React Router
- TanStack Query
- Vite
- Vitest

## 2. 本批范围与非目标

### 2.1 本批必须完成

- 登录页、当前用户态、登出
- 账号模块：
  - 个人信息
  - 修改密码
  - 个人工作量
  - 管理员账号管理
  - 管理员归档路径配置
- 创建任务表单的人员字段自动补全与阻断校验
- 最近任务卡的权限化展示与提交入口
- 工作量模块：
  - 当前流程监视区
  - 历史记录
  - 统计查询
  - 当前节点审批
  - 管理员修复当前节点

### 2.2 本批不做

- 驳回、打回、退回上一环
- 强制通过当前节点
- 历史任务的完整迁移展示
- 修改 IED Excel 来表现流程时间

## 3. 共享业务契约

这一节必须与后端保持完全一致。

### 3.1 最近任务可见性

- `设计人员`：只看自己创建的任务包
- `室主任`：只看本科室创建的任务包
- `所领导`：看全部任务包
- `管理员`：看全部任务包

补充规则：

- 非设计人员在任务卡上要能看到“任务发起者姓名”
- 这里说的是“最近任务”的可见性，不是工作量流程卡的可见性
- 任务创建入口不按角色关闭，`设计人员 / 室主任 / 所领导 / 管理员` 都允许创建和上传任务包

### 3.2 工作量流程卡可见性

- “与我有关”定义为：
  - 我是流程发起人，或者
  - 我是任一审批节点处理人
- 显示规则：
  - `设计人员`：只看与自己有关的流程
  - `室主任`：只看与自己有关的流程
  - `所领导`：只看与自己有关的流程
  - `管理员`：看全部流程
- 未点击“提交”前，不显示该流程卡

### 3.3 人员字段输入规则

对进入工作量流程的字段：

- `ied_prepared_by`
- `ied_checked_by`
- `ied_reviewed_by`
- `ied_approved_by`

执行即时自动补全：

- 输入姓名：按 CSV 查账号并补成 `姓名@账号`
- 输入账号：按 CSV 反查姓名并补成 `姓名@账号`
- 输入 `姓名@错误账号`：仍按姓名修正为正确的 `姓名@账号`
- 如果同名多人：弹出下拉供用户选择具体账号
- 如果找不到合法账号：不允许创建任务包
- `一审` 在界面上虽然只显示一个人，但提交给后端时仍要同时带上 `ied_checked_by` 和 `ied_discipline_leader` 两个字段，且两者值完全一致

例外：

- `ied_chief_designer`（责任设总）不参与自动修正，用户写什么就保留什么

### 3.4 人员重复规则

- `校核者` 与 `工种负责人` 本来就是同一人，在界面上只表现为 `一审`
- 除此之外，只要 `编制者 / 一审 / 二审 / 三审` 出现重复，就不允许创建任务

### 3.5 流程节点与交互

- 提交后，编制者视为已完成
- 工作量流程里的“发起人”以当前登录并点击提交的人为准，只影响流程显示、待办归属和工作量归属，不改 IED Excel，也不回写原始 `ied_prepared_by`
- 后续节点只有：
  - `一审`
  - `二审`
  - `三审`
- 当前节点处理人本人才能点“通过”
- 审批交互只有一种：
  - 输入 `质量折减系数`
  - 点击“通过”

### 3.6 质量折减系数

- 默认值 `1.00`
- 输入范围 `0.80 ~ 1.10`
- 保留两位小数
- 最终工作量：
  - `初始工作量 × 一审系数 × 二审系数 × 三审系数`

### 3.7 自动归档与覆盖提交

- 三审通过后自动归档
- 归档失败时，流程卡变为红色闪烁并保留在“当前流程监视区”
- 系统自动重试，直到归档成功
- 归档成功后从监视区消失，但保留在历史/统计中

提交前需要处理两种弹窗：

- 归档库已有同图册同版本：
  - 提示是否覆盖提交
- 系统内已有同图册同版本进行中流程：
  - 提示是否取消旧流程并重走

### 3.8 工作量统计归属

- 结算时机统一在“归档成功后”
- 统计归属时间分别取：
  - 发起人：归档成功时间
  - 一审：一审通过时间
  - 二审：二审通过时间
  - 三审：三审通过时间

### 3.9 统计可见性

- `设计人员`：只看自己
- `室主任`：看本室所有人
- `所领导`：看全所
- `管理员`：看所有人

历史统计归属使用“结算时科室快照”，后续调科室不反改历史。

账号修改展示规则：

- 未完成任务、进行中流程、当前待办，要跟随后台最新账号信息实时展示
- 已完成历史记录、已结算统计，继续显示当时的历史快照

## 5. 页面与模块改造计划

## 5.1 应用壳与登录态

目标：

- 为整个前端加上登录门槛与当前用户上下文

建议内容：

- App 启动时先请求 `/api/auth/me`
- 未登录：
  - 跳转登录页
- 已登录：
  - 渲染现有工作台
  - 将角色、姓名、科室、待办数挂到全局用户态

页面要点：

- 登录页不需要复杂注册逻辑
- 非设计人员登录后可看到“当前轮到我处理的待办数量”提醒
- 设计人员登录页不显示该提醒

## 5.2 业务模块：创建任务表单

目标：

- 在提交文件前完成人员字段即时补全与阻断校验
- 所有正式角色都使用同一套“创建 / 上传任务包”表单

需要修改：

- `schema.ts` 中的 `nameId` 字段处理
- 交付表单组件
- 提交前校验逻辑

必须支持：

- 用户输入姓名后即时补成 `姓名@账号`
- 用户输入账号后即时补成 `姓名@账号`
- 如果同名多人，弹下拉选择具体账号
- 如果字段无法补全，直接禁用“创建/执行”
- `责任设总` 字段不参与自动修正
- 如果除“一审合并关系”外有人员重复，直接提示并阻止提交
- `一审` 的选择结果要同步写回 `ied_checked_by` 与 `ied_discipline_leader` 两个提交字段

推荐交互：

- 字段下方展示“系统识别到的账号”
- 同名多人时用轻量下拉，不要做全屏弹窗
- 阻断提示写明是哪个字段不合法

## 5.3 业务模块：最近任务卡

目标：

- 保留现有任务卡风格，但让权限和提交动作变清晰

卡片层需要新增的信息：

- 任务创建者姓名
- 当前用户是否可提交
- 当前用户是否可查看详情
- 当前流程状态摘要
- 归档状态摘要
- 初始工作量 / 最终工作量摘要

操作按钮规则：

- “提交”按钮只在创建者本人可用时高亮可点，不区分创建者角色
- 非创建者即使能看见任务卡，也不能点提交

提交前弹窗分支：

- 纠错未通过：
  - 弹出“您图纸中尚有纠错未通过，是否强制启动流程？”
- 归档库中已有同图册同版本：
  - 弹出“当前 {图册编码} 图册已经存在 {版本号} 版，是否覆盖提交？”
- 系统中已有同图册同版本进行中流程：
  - 提示是否取消旧流程并重走

## 5.4 工作量模块：当前流程监视区

目标：

- 把提交后的流程卡平铺展示成可监视、可处理的工作台

界面规则：

- 只显示已提交且尚未归档成功的流程
- 每个流程一个卡片
- 前端需要设计“最多同时显示几张卡”
- 放不下时给出提示
- 已经完成归档的卡片自动从监视区消失

卡片状态表现：

- 轮到当前用户处理：
  - 绿色荧光闪烁
- 与自己有关但还没轮到自己：
  - 灰色静默
- 归档失败：
  - 红色闪烁

卡片内容建议：

- 图册编码 / 版本 / 项目号
- 创建者
- 当前节点
- 一审 / 二审 / 三审进度
- 初始工作量
- 当前质量折减系数
- 审批时间
- 归档状态

## 5.5 工作量模块：审批交互

目标：

- 在流程卡上完成“填写质量折减系数并通过”

交互要求：

- 当前节点处理人才能看到可点击的“通过”
- 点击“通过”时弹出一个小窗：
  - 显示当前节点名
  - 可编辑 `质量折减系数`
  - 默认 `1.00`
  - 限制范围 `0.80 ~ 1.10`
- 没有单独的“保存系数”动作
- 点击通过后立即提交给后端

管理员修复交互：

- 当当前节点异常时，管理员在卡片上看到“修复当前节点”
- 修复方式只有两种：
  - 换人
  - 增加账号信息
- 如果是“增加账号信息”，默认密码固定为 `password`
- 修复成功后，卡片应立即刷新为新的当前待办状态，不需要额外再次提交

## 5.6 工作量模块：历史与统计

目标：

- 把“当前流程监视”和“已结算工作量统计”明确分开

推荐拆分为 2 个子区：

- `当前流程监视`
- `个人工作量统计 / 历史记录`

统计页至少需要支持：

- 时间范围筛选
- 有效记录筛选
- 当前用户权限范围下的汇总

建议展示维度：

- 发起人最终工作量
- 一审工作量
- 二审工作量
- 三审工作量
- 初始工作量
- 质量折减系数
- 统计归属时间
- 结算时科室快照

## 5.7 账号模块

### 普通用户页面

- 显示当前账号信息
- 修改密码
- 查看自己的工作量统计

### 管理员页面

- 账号列表
- 无效账号高亮
- 新增账号
- 修改账号
- 归档根路径配置

账号管理交互规则：

- 账号重复时提示：
  - `账户已存在，是否对该账户进行修改？`
- 点击“是”跳转到该账号的修改窗口
- 同名不同账号允许存在
- 管理员新增账号默认密码固定为 `password`
- 管理员可编辑 `科室编码 / 科室 / 账号 / 姓名 / 角色 / 密码` 全部字段
- 账号修改后，进行中的任务与流程展示要实时刷新为新账号信息；历史记录保持旧快照

## 6. 视觉与交互约束

需要前端设计师重点处理的不是“多几个按钮”，而是“多一套业务节奏”。

### 6.1 必须强化的状态

- 待我审批：绿色闪烁
- 归档失败：红色闪烁
- 只读历史：灰色静默
- 当前流程节点：高亮边框或明显状态条

### 6.2 必须避免的体验问题

- 不要让用户在“最近任务”和“工作量流程卡”之间搞混
- 不要让审批动作藏得太深
- 不要让表单自动补全结果悄悄发生而用户毫无感知
- 不要把管理员修复动作做成普通用户也能误触的入口

### 6.3 推荐的布局思路

- 保持现有站点整体风格一致
- 业务模块继续承载“上传、下载、查看详情”
- 工作量模块专门承载“流程监视、审批、历史、统计”
- 账号模块专门承载“个人信息、密码、管理员配置”

## 7. 当前后端接口补充（2026-03-24）

本节用于覆盖前文里已经过时、或与当前后端真实实现不完全一致的部分。前端联调时，请以本节为准。

### 7.1 认证与全局会话

- `POST /api/auth/login`

  - 请求体：
    - `account_id`
    - `password`
  - 返回：
    - `token`
    - `account`

- `POST /api/auth/logout`

  - Header：
    - `Authorization: Bearer <token>`

- `GET /api/auth/me`

  - Header：
    - `Authorization: Bearer <token>`
  - 返回除账号基础字段外，额外包含：
    - `pending_todo_count`

前端建议：

- 应用启动时先调用 `/api/auth/me`
- 将 `pending_todo_count` 直接挂到全局用户态，不需要前端自行数待办

### 7.2 创建任务包与上传入口

当前管理链仍复用：

- `POST /api/jobs/batch`
- `POST /api/jobs/audit-replace`

补充规则：

- 上传字段名是：`files[]`
- 管理前端发起任务包创建时，应该始终带上：`Authorization: Bearer <token>`
- 如果不带 token，后端仍兼容旧入口，但不会绑定 `owner_snapshot`
- 管理业务线要使用“带登录态的 grouped submission”，不要按匿名旧入口理解

当前 grouped submission 创建成功后：

- 后端会创建 `TaskGroup`
- 如果请求带有效 token，会把创建者快照绑定到 `group.owner_snapshot`

### 7.3 人员字段补全接口

新增：

### 7.4 一审字段规则修正

这一条请覆盖前文所有旧描述。

当前后端真实规则是：

- 一审处理人只来自：`ied_checked_by`
- `ied_discipline_leader` 必须继续提交、继续保存、继续展示
- `ied_discipline_leader` 不再作为一审处理人的回退来源
- 如果 `ied_checked_by` 为空，后端会阻断提交
- 如果 `ied_checked_by` 和 `ied_discipline_leader` 不同，允许提交，一审仍然只取 `ied_checked_by`

前端因此需要改成：

- 页面上可以把“一审”表现为单一角色入口
- 但提交给后端时，仍然必须同时带：
  - `ied_checked_by`
  - `ied_discipline_leader`
- 不要再把这两个字段强制写成相同值

### 7.6 提交流程与冲突弹窗

`POST /api/task-groups/{group_id}/submit` 请求体现在支持：

- `overwrite_archive_existing`
- `cancel_existing_in_progress`

默认都是：

- `false`

后端当前行为：

- 如果归档目标目录已存在，且未明确确认覆盖：
  - 返回 `422`
  - `detail = "archive_target_exists"`
- 如果系统内已有同图册同版次进行中流程，且未明确确认取消旧流程：
  - 返回 `422`
  - `detail = "duplicate_in_progress_exists"`

前端应按两段式处理：

1. 先直接 submit。
1. 如果收到上述 `422 detail`，再弹出对应确认框。
1. 用户确认后，重发 submit，并带上对应布尔值：
   - 覆盖归档：`overwrite_archive_existing = true`
   - 取消旧流程：`cancel_existing_in_progress = true`

补充：

- 当前后端还会校验“谁创建谁提交”
- 如果非创建者尝试提交，后端会返回：
  - `422`
  - `detail = "submitter_must_match_creator"`
- 前端应提前用 `can_submit` 隐藏或禁用按钮，不要依赖报错兜底

`POST /api/task-groups/{group_id}/restart-submit` 请求体与 submit 完全一致，也支持：

- `overwrite_archive_existing`
- `cancel_existing_in_progress`
