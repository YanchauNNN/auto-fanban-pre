## 1. 文档目的

这份计划只以**当前主仓库前端实际代码**为基准，回答三件事：

1. 当前主干前端已经做到了什么。
2. 当前主干前端还缺什么。
3. 后续前端应该按什么顺序继续推进。

如果本文件与旧计划、旧归档冲突，优先级按下面顺序理解：

1. 当前代码
2. [架构.md](./架构.md)
3. 本文件
4. 其他历史计划 / `documents/archieve/*`

## 2. 当前主干前端真实状态

### 2.1 已落地部分

当前主干前端已经落地并可直接联调的部分：

- 首页应用壳
- 顶部系统状态条
- 教程演示入口
- `业务模块 / 账号模块 / 工作量模块` 三个 tab
- 业务模块里的 `出图 / 纠错 / 翻版`
- 任务记录列表
- 独立任务详情页
- 出图配置弹窗
- 纠错配置弹窗
- 翻版配置弹窗
- 本地草稿恢复
- 配置方案保存与复用
- 字体预检与缺失字体替代确认
- `run_audit_check` 联动提交流程
- `plot_style_key` 打印样式切换

### 2.2 尚未落地部分

当前主干里仍未正式接通的部分：

- 登录页
- 全局会话层
- 账号模块真实页面
- 工作量模块真实页面
- `task-groups / workflow / workload / admin` 的前端页面
- 人员字段即时补全与候选选择
- 基于管理业务线的权限壳

### 2.3 当前必须接受的现实

当前仓库存在一个很重要的“前后端错位”：

- 后端管理业务线 API 已经具备较完整能力
- 主干前端仍以业务模块为主
- 首页里的“账号模块”“工作量模块”仍是占位面板

所以后续前端工作不能再按“在已有管理页面上继续补几处”来理解，而应该按“把已经存在的后端能力真正接到主干 UI 上”来推进。

## 3. 当前主干的页面基线

### 3.1 首页

当前首页由 [frontend/src/app/App.tsx](../frontend/src/app/App.tsx) 驱动，真实结构是：

- 顶部状态条
- 模块切换条
- 业务模块面板
- 账号模块占位面板
- 工作量模块占位面板

### 3.2 业务模块

当前业务模块包含两块：

- `新建任务`
- `任务记录`

新建任务区当前支持：

- `出图`
- `纠错`
- `翻版`
- `继续草稿`

任务记录区当前支持：

- 状态筛选
- 搜索
- 展开更多任务
- 进入详情

### 3.3 详情页

当前详情页已经能覆盖：

- 单个出图任务
- 单个纠错任务
- 单个翻版任务
- 交付 + 纠错 group
- 翻版 + 出图 group

## 4. 当前前端与后端的真实接口关系

### 4.1 业务模块当前实际在用的接口

当前主干前端真正依赖的是：

- `GET /api/system/health`
- `GET /api/meta/form-schema`
- `POST /api/jobs/preflight-fonts`
- `POST /api/jobs/batch`
- `POST /api/jobs/audit-replace`
- `GET /api/jobs`
- `GET /api/jobs/{job_id}`
- `GET /api/jobs/{job_id}/download/package`
- `GET /api/jobs/{job_id}/download/ied`
- `GET /api/jobs/{job_id}/download/report`
- `GET /api/jobs/{job_id}/download/replaced`

### 4.2 已就绪但尚未接入主干 UI 的管理接口

后端已经提供，但主干前端还没接上的接口有：

- `POST /api/auth/login`
- `POST /api/auth/logout`

- `POST /api/auth/change-password`
- `GET /api/accounts`
- `GET /api/accounts/invalid-rows`
- `POST /api/accounts/normalize-personnel`
- `POST /api/accounts`
- `PATCH /api/accounts/{account_id}`
- `GET /api/task-groups`
- `GET /api/task-groups/{group_id}`
- `POST /api/task-groups/{group_id}/submit`
- `POST /api/task-groups/{group_id}/restart-submit`
- `GET /api/workflow/monitor`
- `POST /api/workflow/{group_id}/approve`
- `POST /api/workflow/{group_id}/repair-current-node`
- `GET /api/workload/me`
- `GET /api/workload/office`
- `GET /api/workload/institute`
- `GET /api/workload/admin`
- `GET /api/admin/config`
- `PATCH /api/admin/config`

### 4.3 当前必须统一的提交口径

当前前端后端都已经按下面口径工作：

- `POST /api/jobs/batch`
  - `multipart/form-data`
  - `files[]`
  - `params_json`
  - 可选 `run_audit_check`
- `POST /api/jobs/audit-replace`
  - `multipart/form-data`
  - `mode`
  - `files[]`
  - `params_json`

当前提交结构里已经真实存在、并应继续保留的扩展字段：

- `plot_style_key`
- `run_audit_check`
- `source_project_no`
- `target_project_no`
- `run_deliverable`
- `deliverable_params`

这部分现在已经进入 [参数规范.yaml](./参数规范.yaml) 的 `submission_contracts`，后续不应再靠零散 md 口述维持。

## 5. 当前前端需要遵守的业务规则

### 5.1 一审字段规则

这一条以后统一按当前代码和后端交接总说明理解：

- 一审处理人只认 `ied_checked_by`
- `ied_discipline_leader` 继续提交、继续保存、继续展示
- `ied_discipline_leader` 不是一审回退来源
- `ied_checked_by` 与 `ied_discipline_leader` 可以不同

### 5.2 字体预检规则

当前主干已经按下面逻辑工作：

- 上传后先做字体预检
- 若全部 `ok`，直接继续配置
- 若有 `missing_fonts`，弹替代字体确认窗
- 优先使用后端返回的：
  - `replacement_options_by_kind`
  - `default_replacement_fonts`
- 旧的单值字段：
  - `replacement_options`
  - `default_replacement_font`
  只作为兼容项

### 5.3 出图与纠错的组合提交

当前主干不是“先出图，再补建纠错任务”，而是：

- 一次 `createBatch(..., run_audit_check=true)`
- 后端直接建 `TaskGroup`
- 返回 group summary

### 5.4 翻版与出图的组合提交

当前主干翻版流程也已经不是纯草案，而是：

- `replace_only`
  - 直接创建翻版任务
- `replace_with_deliverable`
  - 先采集翻版参数
  - 再进入现有出图配置弹窗
  - 最终通过 `deliverable_params` 一次性提交

## 6. 后续前端工作应该怎么排

### 阶段 1：先把会话壳接进主干

目标：

- 让主干前端先拥有登录态与当前用户上下文

建议落点：

- `frontend/src/shared/session/`
- `frontend/src/features/auth/`
- `frontend/src/app/App.tsx`

完成标准：

- 启动时先调 `/api/auth/me`
- 未登录时显示登录页
- 已登录时进入当前工作台
- 顶栏可展示当前用户、角色、待办数

### 阶段 2：把“最近任务”从 jobs 视角切到 task-group 视角

目标：

- 当前首页业务模块仍可继续展示 `jobs`
- 但真正的“提交/审批/归档”入口要转移到 `task-groups`

原因：

- 当前 `jobs` 更像执行层视角
- `task-groups` 才是管理业务线的主对象

建议落点：

- `frontend/src/features/task-groups/`
- `frontend/src/platform/api/httpAdapter.ts`
- `frontend/src/platform/api/types.ts`

完成标准：

- 能列出 `task-groups`
- 能看 group 详情
- 按后端返回的 `can_submit / can_approve / can_view_detail` 控按钮

### 阶段 3：接工作流监视与审批

目标：

- 让“工作量模块”从占位页变成真实 workflow 页面

建议落点：

- `frontend/src/features/workflow/`
- `frontend/src/features/workload/`

完成标准：

- 接通 `GET /api/workflow/monitor`
- 接通 `approve`
- 接通管理员 `repair-current-node`
- 绿色高亮当前可审批卡片
- 红色高亮归档失败卡片

### 阶段 4：接账号模块

目标：

- 把“账号模块”从占位页变成真实页面

建议拆成两块：

- 普通用户页面
  - `/api/auth/me`
  - `/api/auth/change-password`
- 管理员页面
  - `/api/accounts`
  - `/api/accounts/invalid-rows`
  - `/api/accounts`
  - `PATCH /api/accounts/{account_id}`
  - `/api/admin/config`

### 阶段 5：把人员即时补全接回业务表单

目标：

- 让出图表单开始消费 `normalize-personnel`

当前现实：

- 当前主干业务表单已经能跑通出图
- 但“人员字段即时补全”和“候选选择”还没接

建议落点：

- `frontend/src/features/deliverable/`
- `frontend/src/features/schema/`
- `frontend/src/platform/api/httpAdapter.ts`

完成标准：

- `ied_prepared_by / ied_checked_by / ied_reviewed_by / ied_approved_by` 可即时补全
- 歧义时可选候选账号
- 无法解析时阻断提交
- `ied_chief_designer` 仍保持自由输入

## 7. 当前不建议做的事

- 不要再把“账号模块”“工作量模块”继续写成文档里的已完成页面
- 不要继续围绕旧 `jobs` 视图堆管理功能
- 不要把 `ied_discipline_leader` 再强制覆盖成 `ied_checked_by`
- 不要把字体替代逻辑重新写回前端静态表
- 不要绕过 `submission_contracts` 再新增一套零散提交字段

---

## 8. 推荐验收顺序

按当前主干继续推进前端，推荐验收顺序是：

1. 登录壳与当前用户态
2. task-group 列表与详情
3. submit / restart-submit 冲突弹窗
4. workflow monitor / approve / repair
5. 账号模块与管理员配置
6. 工作量查询页
7. 人员字段即时补全
