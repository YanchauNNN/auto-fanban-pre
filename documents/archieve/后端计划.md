## 1. 文档目的

本文档面向后端工程师，目标是把以下 3 条新业务线拆成可以直接编码的后端实施计划：

- 账号管理与登录认证
- 工作量流程与统计结算
- 自动归档与覆盖提交

本文默认沿用当前仓库的既有原则：

- 新功能继续复用 `TaskGroup + Job + storage/*` 持久化体系。
- “机制参数”落入 YAML；“运行态数据”落入 `group.json / job.json / CSV / JSON`。
- 不引入数据库。
- 所有新上传交付任务统一进入“任务包”语义，即统一以 `TaskGroup` 为主载体。

## 2. 本批范围与非目标

### 2.1 本批必须完成

- 登录、登出、当前用户查询、修改密码
- 管理员新增/修改账号，回写 `documents_bin/姓名角色表.csv`
- 按创建者账号快照控制“最近任务”可见性
- 创建任务时的人员规范化、重复校验、阻断校验
- 提交流程、审批流转、质量折减系数、时间记录
- 初始工作量计算、最终工作量结算、个人/科室/全所统计查询
- 审定后自动归档、归档失败自动重试、覆盖提交

### 2.2 本批明确不做

- 独立数据库
- 审批“驳回 / 打回 / 退回上一环”
- 强制通过当前节点
- 修改 IED 计划 Excel 本身来承载流程时间
- 历史老任务的数据回填迁移

## 3. 共享业务契约

这一节必须与前端保持完全一致。

### 3.1 任务包与历史兼容

- 所有新的上传交付任务都统一创建为 `TaskGroup`。
- 不区分角色来源，`设计人员 / 室主任 / 所领导 / 管理员` 都允许创建和上传任务包。
- 历史老任务继续保留可查，但默认仅管理员可见。
- 老任务不强行补齐“创建者快照 / 流程快照 / 工作量快照”。

### 3.2 账号与角色

- 账号主数据源：`documents_bin/姓名角色表.csv`
- 只认 4 种正式角色：
  - `设计人员`
  - `室主任`
  - `所领导`
  - `管理员`
- `账号` 必须唯一。
- `姓名` 允许重复。
- 如果 CSV 某一行角色非法、账号为空、关键字段缺失，则该行标记为“无效账号”：
  - 不能登录
  - 不能参与流程分发
  - 需要在管理员界面高亮提示修复
- 普通用户已登录时可以直接修改自己的密码，不要求先输入旧密码。
- 密码修改必须回写 CSV。
- 管理员新增账号时，默认密码固定写入 `password`。
- 管理员修改账号后：
  - 未完成任务、进行中流程、当前待办都要跟随新的账号信息继续流转
  - 已完成历史记录、已结算工作量继续保留当时的快照，不反改历史

### 3.3 科室与层级

- 任务归属按“创建者账号表中的科室”判定。
- 如果创建者科室是 `建筑结构所`，则该任务直接归属“所部级”。
- 第一版在 YAML 中显式声明层级关系，例如：
  - `建筑结构所 -> [结构一室, 结构二室, 建筑总图室]`

### 3.4 最近任务可见性

- `设计人员`：只看自己创建的任务包。
- `室主任`：看本科室创建的任务包。
- `所领导`：看全部任务包。
- `管理员`：看全部任务包。
- 非设计人员查看任务卡时，卡片上需要附带显示“任务发起者姓名”。

### 3.5 流程可见性

- 工作量流程卡的可见性与“最近任务”可见性不同。
- “与我有关”的定义：
  - 我是流程发起人，或者
  - 我是任一审批节点处理人
- 可见范围：
  - `设计人员`：只看与自己有关的全部流程
  - `室主任`：只看与自己有关的全部流程
  - `所领导`：只看与自己有关的全部流程
  - `管理员`：看全部流程
- 未点击“提交”前，工作量模块中不显示该流程卡。

### 3.6 表单中的人员字段规则

- 进入工作量流程的字段统一按“标准格式 `姓名@账号`”处理：
  - `ied_prepared_by`
  - `ied_checked_by`
  - `ied_reviewed_by`
  - `ied_approved_by`
- `ied_discipline_leader` 在业务上与 `ied_checked_by` 视为同一人，不再独立选择。
- 后端在保存规范化结果时，仍要把 `ied_discipline_leader` 自动补齐为与 `ied_checked_by` 相同的标准化值，避免前端只显示 `一审` 后下游文档生成链缺参。
- `ied_chief_designer`（责任设总）完全例外：
  - 用户写什么就保留什么
  - 不做自动修正
  - 不参与流程分发

人员自动修正规则：

- 只填姓名：按 CSV 查人并补成 `姓名@账号`
- 只填账号：按 CSV 反查姓名并补成 `姓名@账号`
- 填了 `姓名@错误账号`：仍优先按姓名查 CSV，并修正为正确的 `姓名@账号`
- 如果姓名查到多个账号：前端弹下拉，用户选定具体账号后再补齐
- 如果无法解析出合法账号：连“创建任务包 / 执行任务包”都一起拦住

### 3.7 人员重复规则

- 允许重复且必须重复的只有一组：
  - `校核者 = 工种负责人`
- 除此之外，只要 `编制者 / 一审 / 二审 / 三审` 出现同一账号重复，就不允许创建任务。

### 3.8 提交与审批流程

- 普通路径下只能“谁创建谁提交”。
- 点击“提交”后，等价于“编制者节点已完成”。
- 工作量流程中的“发起人 / 编制者处理人”以当前登录并点击提交的人为准：
  - 只覆盖流程归属、待办分发、工作量归属
  - 不回写 `ied_prepared_by`
  - 不修改 IED Excel 本身
- 后续只保留 3 个审批节点：
  - `一审`：校核者 + 工种负责人合并
  - `二审`：审核者
  - `三审`：审定者
- 普通情况下只有“当前节点处理人本人”能点通过。
- 管理员不做强制通过，只做：
  - 给当前节点换人
  - 增加新账号后再换人

### 3.9 质量折减系数与工作量

- 每个审批节点都有一个 `质量折减系数`
- 默认值 `1.00`
- 允许范围 `0.80 ~ 1.10`
- 保留两位小数
- 审批动作只有一种：
  - 填写系数并通过
- 不做“先保存系数、稍后通过”的两步交互

工作量口径：

- 初始工作量：由图幅折算 A1 后求和
- 最终工作量：
  - `initial_workload_a1 * one_review_factor * two_review_factor * three_review_factor`
  - 结果保留两位小数
- 记账对象：
  - 发起人最终工作量
  - 一审工作量
  - 二审工作量
  - 三审工作量
- 第一版中，后三者的数值先默认等于“发起人的最终工作量”
- 只有“归档成功”后才正式结算入账
- 入账后使用不同统计归属时间：
  - 发起人：归档成功时间
  - 一审：一审通过时间
  - 二审：二审通过时间
  - 三审：三审通过时间

### 3.10 自动归档

- 不再设置手工归档按钮。
- `三审` 通过后自动归档。
- 归档内容：
  - 交付压缩包
  - `IED计划.xlsx`
  - 上传原始 DWG
- 归档目录层级：
  - `{engineering_no}/{subitem_no}/{album_internal_code}/{revision}`
- 归档根路径由管理员配置。
- 路径值放在新的 `config.json` 中；路径机制和文件位置写入 YAML。
- 同名覆盖允许。

### 3.11 覆盖提交与重复流程

点击“提交”时，需要同时检查两类冲突：

- 归档库中是否已经存在“同图册编码 + 同版本”
- 系统中是否已经存在“同图册编码 + 同版本”的进行中流程

规则如下：

- 如果归档库已存在：
  - 弹窗确认是否覆盖提交
  - 选“否”则取消本次提交
  - 选“是”则允许继续
- 如果系统中已有进行中流程：
  - 提示用户是否取消旧流程并重走
  - 选“是”：
    - 旧进行中流程直接终止并删除干净
    - 当前流程接管
  - 选“否”：取消本次提交
- 如果已存在的是“历史成功记录”：
  - 旧记录要等“新这次也归档成功”之后再删除
- 覆盖归档时：
  - 先清空目标版本目录
  - 再把本次新产物整套重新归档进去
- 覆盖成功后：
  - 旧记录彻底删除，不保留历史
  - 旧工作量不再计入有效统计
  - 只保留最新覆盖成功的那次作为有效记录

### 3.12 归档失败

- 流程不算完成。
- 当前流程卡进入“归档失败”状态并红色闪烁。
- 系统自动重试归档，直到成功为止。
- 归档成功后：
  - 从“当前流程监视区”消失
  - 仍保留在个人工作量统计 / 历史记录中

## 7. 接口拆分计划

## 7.1 认证接口

- `POST /api/auth/login`
- `POST /api/auth/logout`
- `GET /api/auth/me`
- `POST /api/auth/change-password`

`/api/auth/me` 需要返回：

- 当前账号信息
- 当前角色
- 当前科室
- 当前登录态是否有效
- 当前待办数量

## 7.2 账号管理接口

- `GET /api/accounts`
- `POST /api/accounts`
- `PATCH /api/accounts/{account_id}`
- `GET /api/accounts/invalid-rows`

规则：

- 账号重复时提示“账户已存在，是否对该账户进行修改？”
- 只有账号重复才触发跳转到修改窗口
- 同名不同账号允许存在
- 管理员新建账号默认密码固定为 `password`
- 管理员可修改 `科室编码 / 科室 / 账号 / 姓名 / 角色 / 密码` 全部字段
- 账号修改生效后，未完成任务与进行中流程需要重新绑定到新账号信息

## 7.3 任务包接口

建议新增单独的任务包接口，而不是继续完全依赖 `/api/jobs`：

- `GET /api/task-groups`
- `GET /api/task-groups/{group_id}`
- `POST /api/task-groups/{group_id}/submit`
- `POST /api/task-groups/{group_id}/restart-submit`

返回结构中必须显式给出：

- 当前用户是否可见
- 当前用户是否可提交
- 当前用户是否可审批
- 创建者姓名/账号/科室
- 流程状态
- 工作量摘要
- 归档状态

## 7.4 工作量流程接口

- `GET /api/workflow/monitor`
- `POST /api/workflow/{group_id}/approve`
- `POST /api/workflow/{group_id}/repair-current-node`

审批请求至少包含：

- `node_key`
- `factor`

管理员修复请求至少支持：

- `replace_with_account_id`
- `create_account_payload`
- 如果走 `create_account_payload`：
  - 新账号默认密码写入 `password`
  - 创建成功后立即作为当前节点新处理人
- 修复成功后，流程必须立即恢复成该节点的“待办中”状态，不需要二次提交

## 7.5 工作量统计接口

- `GET /api/workload/me`
- `GET /api/workload/office`
- `GET /api/workload/institute`
- `GET /api/workload/admin`

所有统计接口都应支持：

- 时间范围筛选
- 状态筛选
- 是否只看有效记录

## 7.6 管理员配置接口

- `GET /api/admin/config`
- `PATCH /api/admin/config`

第一版仅处理：

- `archive_root_path`

## 9. 删除与替换策略

必须区分 3 种删除：

- 删除“进行中旧流程”
  - 用户在重复流程弹窗中选择“重新走”
  - 旧流程直接删干净
- 删除“旧成功记录”
  - 覆盖提交流程新归档成功后执行
- 删除“旧归档目录”
  - 覆盖归档前先清空版本目录

删除时需要同步处理：

- `group.json`
- 子 `job.json`
- 任务目录
- 归档目标目录
- 统计有效性

## 12. 后端验收标准

- 所有新上传任务都变成任务包
- 非设计角色也能创建和上传任务包
- 非法人员配置无法创建和执行

- 工作量统计按个人 / 本室 / 全所 / 全部权限返回正确数据
- 进行中流程跟随账号修改；已完成历史与统计保持原快照
